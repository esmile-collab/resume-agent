# 本地可跑开发流程规划（Resume Fit Agent）

版本：v0.1  
日期：2026-02-27

---

## 1. 目标定义（本轮）

基于当前 PRD/架构文档，先交付一个 **本地可跑、可复盘、可扩展** 的 MVP 实现，满足：

1. 可在本地完成主链路：`项目初始化 -> 上传简历/JD -> 方向聚类预览 -> 确认分配 -> 评分 -> 生成 -> 版本产物落盘`。
2. 数据可追溯：`Project/TaskCard/ArtifactVersion/Run/Memory` 全部本地可查。
3. 模块化实现：路由、评分、生成、存储、接口可独立替换。
4. 可演示：CLI 必须可用；Web API 为可选增强（不阻塞 MVP）。

---

## 2. 模块化拆分

### M0. 工程脚手架与运行基线

**范围**
1. Python 3.11+ 项目初始化
2. 统一配置（`.env` + settings）
3. 日志与错误码规范
4. 一键脚本：`bootstrap/dev/test`

**产出**
1. 目录骨架
2. `README.md` 最小启动说明
3. `scripts/bootstrap.sh`、`scripts/dev.sh`、`scripts/test.sh`

**完成标准**
1. 空目录拉起后 15 分钟内可跑通 hello flow

---

### M1. Persistence（SQLite + 本地文件）

**范围**
1. 落地核心表：`projects/project_jd_entries/task_cards/card_jd_links/jd_allocation_logs/artifact_versions/runs/task_memory_facts/messages`
2. 本地产物目录：`.data/artifacts/<project_id>/...`
3. 仓储层（Repository）与事务边界

**产出**
1. DB schema + migration
2. Artifact 存取服务
3. 项目重启后状态恢复能力

**完成标准**
1. 新建项目、写入JD、创建卡片、保存版本后，重启仍可读

---

### M2. Core State + Router（最关键）

**范围**
1. 6 意图：`ingest_jd/update_resume/add_info/generate/compare/abandon`
2. 5 状态：`pending/scored/generating/completed/abandoned`
3. 低匹配风险确认流程
4. 乱序输入处理（卡内新增JD上收 Project 分配器）

**产出**
1. `input_router`
2. `task_state_manager`
3. 路由决策引擎（含 state transition）

**完成标准**
1. 路由测试覆盖：正常链路 + 低匹配 + 乱序输入

---

### M3. Domain Tools（可替换实现）

**范围**
1. `jd_parser`
2. `project_jd_allocator`
3. `resume_parser`
4. `scorer`（S100 + match_level）
5. `improver`
6. `reviewer`

**产出**
1. 工具接口严格对齐 `TOOLS_SCHEMA.md`
2. 每个工具可单测
3. 先规则版/Mock 版跑通，再接入 LLM 增强

**完成标准**
1. 任一工具失败不导致状态损坏（有错误恢复）
2. 评分结果能回写任务卡并驱动路由

---

### M4. Orchestration Use Cases（端到端编排）

**范围**
1. Project 级流程：初始化、JD 批量预览确认、卡片创建更新
2. Card 级流程：评分、补充信息、生成（normal/compensation）
3. 版本锁定与证据绑定

**产出**
1. 用例服务层（UseCase）
2. 端到端流程测试（fixtures）

**完成标准**
1. 10 条 JD -> 2 方向 -> 2 卡 -> 2 份输出全链路通过

### M7. 质量与可运维性

## 4. 开发顺序（保证“随时可演示”）

1. M0 -> M1：先把“能存、能读、能恢复”打牢。
2. M2：路由状态机先行，保证流程可控。
3. M3：工具先最小可用实现（规则/Mock），保证主链路先跑通。
4. M4 + M5：拉通 CLI 端到端。
5. M6：再补 API，不影响 CLI 可交付。
6. M7：做稳定性、压缩和埋点。

---

## 5. 对齐机制（你可随时查看进度）

### 5.1 进度看板（固定模板）

每个模块统一四个状态：
1. `todo`
2. `in_progress`
3. `blocked`
4. `done`

每次状态更新必须附：
1. 已完成项
2. 运行证据（命令 + 核心输出）
3. 风险与下一步

### 5.2 每个模块的“可验收证据”

1. 必须有至少 1 个可执行命令
2. 必须有至少 1 条自动化测试（或最小冒烟测试）
3. 必须有 1 段示例输入与输出

### 5.3 沟通节奏（建议）

1. 开始模块前：我先给你“目标/边界/风险”三行确认
2. 模块开发中：每 20-40 分钟汇报一次进度
3. 模块完成后：给你一份“验收清单 + 演示命令 + 未决问题”

---

## 6. 风险前置

1. LLM 不稳定：先规则实现 + 固定样例，保证本地可跑不依赖模型波动。
2. 路由复杂度膨胀：严格限定 6 意图 / 5 状态，不提前扩展。
3. 数据污染：坚持 Project 与 Task Card memory 隔离。
4. 需求漂移：所有新增需求先映射到模块，不跨模块直接改。
