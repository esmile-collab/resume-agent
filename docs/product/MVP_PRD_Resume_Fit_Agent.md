# MVP PRD - 投递匹配度质检 Agent（Resume Fit Agent）

版本：v0.3  
日期：2026-02-27  
负责人：

---

## 1. 背景与问题

校招/实习阶段普遍存在“海投”，但候选人往往只用一份通用简历投递多个岗位方向，导致：
1. JD 关键词覆盖不足。
2. 经历叙事与岗位关注点错位。
3. 面试复述准备不足，容易在追问中失分。

用户真实诉求不是“写得更好看”，而是“投递前最后一步的匹配度决策和可执行优化”。

---

## 2. 产品定位与范围

### 2.1 MVP 定位

本产品是一个“可复盘的求职决策引擎”，而不是普通聊天改写器。  
核心在：评分、路由、状态、证据、风险确认。

### 2.2 MVP 目标

1. 在一个 `Project` 内支持多方向投递准备（`Task Card`）。
2. 每个方向可独立完成“评分 -> 补充 -> 生成 -> 复核”。
3. 每次生成结果可追溯到对应 JD/简历版本与改动证据。
4. 所有 JD 统一归属 `Project`，由分配器路由到合适的 `Task Card`。

### 2.3 非目标（MVP 不做）

1. 自动搜索 JD。
2. 自动跨卡同步补充经历。
3. 卡片数量硬限制。
4. 批量投递渠道打通。

---

## 3. 核心对象模型

### 3.1 Project（项目层）

定义：一次投递周期容器（如“暑期实习”“秋招”）。

职责：
1. 持有基础简历版本（共享层）。
2. 持有 JD 资产池（单条/批量上传后的标准化 JD 条目）。
3. 管理多个方向任务卡与 JD->Card 引用关系。
4. 记录聚合统计（`jd_count`、`direction_count`、`resume_output_count`）。

### 3.2 Task Card（方向层）

定义：一个 JD 方向对应一张任务卡（如策略产品、功能产品）。

职责：
1. 维护该方向的 JD 引用集合（非 JD 原文主存）。
2. 维护该方向私有补充信息。
3. 维护该方向评分、生成状态与最终简历版本。

### 3.3 Artifact Version（版本层）

定义：JD/简历/输出结果的不可变快照。

规则：
1. 只新增版本，不覆盖历史。
2. 每次生成绑定输入版本与输出版本。

---

## 4. 用户主流程（更新后）

1. 用户创建或进入 `Project`。
2. 在 `Project` 上传基础简历。
3. 在 `Project` 上传 JD（可单条或批量）。
4. 系统执行 JD 拆分与方向聚类，输出“方向预览”（含 `jd_count`/`direction_count`/建议卡片映射）。
5. 用户回复“确认创建/更新卡片”（或使用快捷词），系统批量生成或更新 `Task Card` 并写入 JD 引用关系。
6. 进入卡片对话：系统评分并展示评分卡。
7. 用户按需要补充该方向信息（仅作用于当前卡）。
8. 用户触发生成：
   - 高/中匹配：正常生成。
   - 低匹配：先风险确认，再决定是否补偿生成。
9. 系统输出该卡的最终结果：方向简历、改动说明、评分卡、面试复述题。

补充入口：
1. 用户在 `Task Card` 内新增 JD 时，事件仍路由到 `Project` 级 JD 分配器。
2. 分配器决策三选一：加入当前卡 / 迁移到已有卡 / 新建卡并加入。

## 5. MVP 功能需求

### 5.1 输入

1. 基础简历（文本或 PDF）。
2. JD 输入（单条或多条，入口可在 Project 或 Task Card）。
3. 卡片内补充信息（对话输入）。

### 5.2 JD 接入、聚类与分配（Project 级）

1. 识别 `jd_count`（JD 条目总数）。
2. 方向聚类得到 `direction_count`（基于叙事框架差异）。
3. 产出规划得到 `resume_output_count`（默认与方向数一致）。
4. 聚类结果先展示“方向预览”，由用户确认后再创建/更新卡片。
5. 所有 JD 原文和解析结果写入 Project 资产池。
6. 通过 `project_jd_allocator` 维护 JD->Card 引用关系。
7. 分配决策：
   - `assign_current_card`
   - `assign_existing_card`
   - `create_new_card`

### 5.3 对话路由（Intent + State）

核心意图（6个）：
1. `ingest_jd`
2. `update_resume`
3. `add_info`
4. `generate`
5. `compare`
6. `abandon`

意图口径补充：
1. 卡片内“新增JD”不新增第7意图，统一归入 `ingest_jd`（入口别名 `add_jd`）。
2. `ingest_jd` 支持 `source_scope=project|task_card`，但数据写入统一在 Project 层完成。

核心状态（5个）：
1. `pending`
2. `scored`（含 `match_level` 属性）
3. `generating`（`mode=normal|compensation`）
4. `completed`
5. `abandoned`

### 5.4 评分系统（S100）

七维评分（详见《评分系统设计_v1.md》）：
1. 公司级别匹配度（10）
2. 业务级别匹配度（15）
3. 行业匹配度（10）
4. 岗位经验匹配度（20）
5. 能力匹配度（20）
6. 真实性可信度（15）
7. 可复述性（10）

总分：`S100 = 0-100`

匹配分层：
1. `high`（>=75）
2. `medium`（50-74）
3. `low`（<50）

说明：分层用于“推荐策略”，不作为硬阻断。

### 5.5 生成与风控

1. `high/medium`：支持直接生成。
2. `low`：必须先风险确认。
3. 风险确认通过后进入补偿模式生成（不虚构经历）。
4. 风险确认取消则停留在当前卡评分页。

### 5.6 Memory 规划

Project 共享层：
1. 基础简历版本。
2. 项目元信息。
3. JD 资产池（原文、解析结果、聚类结果）。
4. JD 分配日志（分配到哪个卡片及理由）。

Task Card 私有层：
1. 该方向补充经历。
2. 该方向 JD 澄清信息（补充字段，不存 JD 原文）。
3. 该方向对话内约束。

明确约束：
1. 卡片补充信息不自动同步到其他卡片。
2. 卡片补充信息不自动上升到 Project 共享层。
3. JD 原文不落 Task Card 私有层，Task Card 仅保存 JD 引用关系。

### 5.7 版本与复盘

1. 每次评分和生成都写入运行记录（Run）。
2. 每次输出绑定证据来源（JD片段/简历片段/补充信息）。
3. 每个任务卡保留“当前最终版”与历史版本链。

### 5.8 输出

每个 Task Card 输出：
1. 定制简历（该方向最终版）。
2. 改动说明（改动点 + 原因 + 证据）。
3. 面试复述题库。
4. 评分卡（总分 + 维度分 + 分层建议）。
5. 低匹配场景下的补偿内容包（如触发）。

Project 聚合输出：
1. `jd_count`
2. `direction_count`
3. `resume_output_count`

## 6. 必须实现的交互规则（本轮确认）

1. **JD 偏离方向提醒**
- 如果用户在某卡上传的 JD 与该卡方向明显不一致，系统提示：
  “该JD可能属于另一个方向，是否新建卡片或移动到其他卡片？”

2. **批量JD预览确认**
- 用户一次上传多条 JD 后，系统先展示聚类预览；
- 用户通过自然语言确认（如“确认创建”）后，才批量创建/更新 Task Card。

3. **评分不阻断生成**
- 评分只做策略建议，不直接禁止用户生成。

4. **生成结果版本锁定**
- 每次生成形成独立版本号；卡片显示“当前最终版”。

5. **基础简历更新策略**
- 用户更新 Project 基础简历后，不自动覆盖已完成卡片结果；
- 系统仅提示用户可在指定卡片手动重新生成。

6. **卡片内新增JD统一上收**
- 在 Task Card 内触发“新增JD”时，必须上收到 Project 路由器再分配；
- 不允许直接写入当前卡片绕过分配校验。

7. **对话优先交互**
- 产品默认以单对话框推进流程，系统通过推荐语言引导下一步；
- 按钮/快捷选项仅作为兜底，不应成为主路径。

8. **展示层保留**
- 必须保留 JD 拆分/聚类/评分/生成阶段的 loading 反馈；
- 必须保留评分卡、风险卡、版本结果卡等结构化信息展示。

---

## 7. 乱序输入处理规则

1. 用户在卡 A 对话中补信息时又上传新 JD：
- 新 JD 先进入 Project 资产池，再由分配器决定归属（当前卡/已有卡/新卡）。

2. 用户在已完成卡继续补充：
- 仅更新该卡私有信息；是否重算由用户主动触发。

3. 用户跨卡切换：
- 始终读取该卡私有信息 + Project 基础简历版本。

4. 用户在卡片内新增 JD：
- 事件归类为 `ingest_jd(source_scope=task_card)`；
- 处理路径与 Project 上传 JD 一致，仅入口不同。

## 8. 指标与评测

### 8.1 结果指标

1. 方向卡生成完成率。
2. 用户采纳率（对最终版接受程度）。
3. 低匹配风险确认通过率。
4. 证据覆盖率（改动有证据绑定比例）。

### 8.2 过程指标

1. 各状态分布（`pending/scored/generating/completed/abandoned`）。
2. 生成耗时。
3. 卡片内补充信息使用率。
4. 补偿模式触发率。

---

## 9. 风险与对策

1. 虚构风险：强制证据绑定 + 低匹配风险确认。
2. 方向混淆：JD 偏离方向提醒 + 手动迁移建议。
3. 上下文污染：卡片私有信息不跨卡自动同步。
4. 结果混乱：版本锁定 + 当前最终版标识。

---

## 10. 技术约束（MVP）

1. 基于 Claude Agent SDK。
2. 单 Agent 工作流。
3. 模块化工具链：`jd_parser/resume_parser/scorer/improver/reviewer/task_state_manager`。
4. 本地优先可部署（详见《本地优先部署与Memory规划.md》）。

---

## 11. MVP 验收标准

1. 用户可在一个 Project 内创建多个 Task Card 并独立完成生成。
2. 卡片补充信息仅作用于当前卡片，不影响其他卡片。
3. 低匹配场景必须出现风险确认，确认后才能补偿生成。
4. 每个卡片都可查看“当前最终版”及历史版本。
5. 用户更新基础简历后，已完成卡片不被自动覆盖。
6. 多 JD 上传可先看到聚类预览，确认后批量创建/更新卡片。
7. 卡片内新增 JD 会统一路由到 Project 分配器，不会绕过分配规则直接入卡。
