# 评分系统设计 v2.1

版本：v2.1  
状态：现行  
对应实现：`src/scoring/campus_scorer.py`

## 1. 文档定位

本文档只描述当前仓库真正落地的评分子系统，不再重复旧版评分稿的方案比较。当前评分器服务于 `resume_score` 工具，目标是输出一个可解释、可落盘、可在前端展示的匹配度报告。

## 2. 输入输出

### 输入

1. `jd`：目标岗位描述全文。
2. `resume`：基础简历或由 memory 聚合出的经历文本。
3. `rule_weight`：规则分与软分的权重分配，当前默认 `0.4`。

### 输出

`ScoreReport`，核心字段包括：

1. `final_score`
2. `match_level`
3. `suggestion`
4. `risk_warning`
5. `quick_improvements`
6. `long_term_improvements`
7. `hard_score / soft_score / evidence`

## 3. 评分结构

### 3.1 硬性指标

当前规则分由以下维度组成：

1. 实习经历
2. 项目经历
3. 技术实践
4. 学历层次
5. 专业匹配
6. GPA
7. 英语能力
8. 稳定性

### 3.2 软性指标

当前软分由以下维度组成：

1. 学习能力
2. 执行能力
3. 沟通表达
4. 数据意识
5. 稳定性
6. 适应性
7. 简历逻辑

## 4. 运行方式

1. 评分器先做一次“参数抽取 + 软分评估”。
2. 再基于抽取结果计算规则分。
3. 最后合成总分并生成报告对象。

如果没有可用 LLM 客户端，评分器仍会返回降级结果，只是信息密度更低。当前实现会优先尝试：

1. `Anthropic`
2. `OpenAI`
3. 无可用客户端时走最小降级路径

## 5. 产品约束

1. 评分是建议，不是硬阻断。
2. 评分报告必须能在 artifact 中持久化，并可回到前端查看。
3. 评分要为生成和润色提供“缺口”和“建议”，不是只给总分。
4. 当前版本优先追求可解释和可演示，不追求复杂的岗位专属专家系统。

## 6. 与主链关系

1. `resume_score`：直接消费本评分器输出。
2. `resume_generate`：先评分，再生成。
3. `resume_polish`：先评分和分析，再决定 patch 重点。
4. `ScorePanel`：展示最近一次 score artifact 详情。

## 7. 后续收敛方向

1. 清理旧版评分设计文档中已经退出现行实现的部分。
2. 把评分器的降级路径、模型配置和失败提示整理成更稳定的工程接口。
3. 在 demo 可稳定部署后，再讨论更复杂的岗位专属评分策略。
